## 2026-10-31 WSL2 clock runs ~1.9 % fast and is stepped back every 32 s
severity: soft
what: inside WSL the kernel clock tick, nominally 10000 µs, is re-set about every 8 s to values between 10160 and 10238 µs (results/0/tick-watch.json, results/0/tick-watch-2.json). So CLOCK_MONOTONIC and the wall clock gain +1.6 to +2.4 %, about 1.94 % on average. systemd-timesyncd polls every 32 s, finds the clock ~0.6 s ahead and steps it back. One llama-bench repetition was cut 0.622 s short by a step. Evidence: NOTEBOOK.md "Phase 0.5–0.6", results/0/clock-steps.json, results/0/timesync-snapshot.txt.
tried: measured it, and worked around it: same-session ratios, CUDA events for absolute GPU timing, a screening rule for llama-bench, and the tick recorded at every preflight (STATE.md Decisions).
owner action: none required (for information). Optional: to find out whether a fresh WSL boot has a normal clock, run `wsl --shutdown` in Windows, reopen WSL, then run `timedatectl timesync-status` in the repo. The Offset should be a few ms, not about −600 ms. Also run `bench/timesync_snapshot.sh "10 min ago" now`; it should show tick=10000. `python bench/tick_watch.py --seconds 60 --out /tmp/tick.json` shows whether the tick still moves. If the problem comes back, `sudo systemctl disable --now systemd-timesyncd` should stop the 32 s steps (WSL2 takes its time from Windows). Whether it also stops the tick being re-set isn't known. The reviewer suspects two time-sync loops fighting each other, and if that's right it might.
