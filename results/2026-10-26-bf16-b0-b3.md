# bf16 free-text speed-up experiments, Qwen3.5-0.8B (2026-10-26)

Goal: speed up ONE continuous free-text reply, single stream, non-quantized (bf16) 0.8B target. No parallel/batched/sub-task methods.
Hardware: RTX 3050 Laptop 4 GB, i5-13420H, plugged in, Balanced plan; nothing in the system was changed. llama.cpp CUDA b11884 (commit 63412d873).
Labels: **[measured]** = measured here, **[est]** = estimate from the research note (not measured), **[unv]** = unverified guess.

## Method (all sessions)
- Prompt set: the 6 free-form prompts F1-F6 from prompts/prompts.json (essay, story, explanation prompts; no copy-heavy prompts). Chat template, thinking disabled, greedy (temperature 0, seed 1), `cache_prompt=false`, n_predict 256 (all six reached 256 tokens in every pass; except the 512 test where F1 stopped at EOS after 326).
- Server configs: fresh llama-server per config, GPU-idle check before each (nvidia-smi 0 % util, <300 MiB used, no stray llama processes), one warm-up pass over the 6 prompts discarded, then 5 timed passes. One pass = sum(generated tokens)/sum(server `predicted_ms`) over the 6 prompts. Mean +/- SD is over the 5 passes. Common flags: `-ngl 99 -fa on -np 1 -kvu -c 4096`, `-t/-b/-ub` default (the server resolves `-t` to 8, `-b 2048 -ub 512`).
- llama-bench configs: `-p 0 -n 256 -r 5` (bench discards its own warm-up); mean +/- SD of 5 reps. Bench default is `-t 8`, `-fa` explicit on, no sampling.
- Speedup = config mean / control mean (+/- propagated SD). The control (plain bf16 server) is re-run at the end of each session. "vs control" in the first table uses the mean of the start and end controls (bracket mean); where drift matters I also quote the adjacent control.
- Raw data: `2026-10-26-bf16-B1-overhead.raw.json.gz` (B1), `...-B2-backend-sampling.raw.json`, `...-B3-mtp.raw.json` (B2/B3 added below). Server logs are in logs/ (git-ignored).
- Loops: for every pass I compute the duplicate-4-gram rate and the max repeat count of any 6-word sequence; "loop" = dup4 >= 0.30 or some 6-gram >= 3 times.

## Is the model really bf16?
`scripts/gguf_tensors.py`: the bf16 GGUF (`Qwen_Qwen3.5-0.8B-bf16.gguf`, 1.56 GB) has all weights as BF16 (type 30) and **already contains the MTP block** (`blk.24.nextn.*`, `nextn_predict_layers = 1`, the Q4_K_M bartowski file too). So MTP on the bf16 target works with the existing file; no download was needed [measured]. The f16 GGUF used in B1 was made with `llama-quantize --allow-requantize <bf16> <f16> F16` (4 s).

## B0/B1: reconciling llama-bench vs llama-server, then overhead toggles
Env var names present in this build (strings in the DLLs) [measured]: `GGML_CUDA_DISABLE_GRAPHS`, `GGML_CUDA_GRAPH_OPT`, `GGML_CUDA_DISABLE_FUSION` (ggml-cuda.dll), `LLAMA_GRAPH_REUSE_DISABLE` (llama.dll). All four exist. `-bs/--backend-sampling` exists.

### Short answer: the 51 vs 71 tok/s gap did NOT reproduce
- llama-bench today, bf16, `-ngl 99 -fa on -p 0 -n 256 -r 5`: **71.74 +/- 0.10 tok/s**; with the earlier baseline's exact style (`-p 512 -n 128`): 71.54 +/- 0.11; with `--no-warmup`: 70.42 +/- 0.03. The old baseline file said 51.47 +/- 4.93 (r=3, taken at ~09:50 in the same day, first model run of the day, SD of 10 %). [measured]
- The server with identical flags: 69.45 +/- 0.20 (start control). Real remaining bench-over-server gap: **+3.3 % (13.94 vs 14.40 ms/token, 0.46 ms)**. `-np 1 -kvu` vs `-np 1` vs auto slots make no difference (69.59 / 69.56 vs 69.45; within 0.2 %). [measured]
- So the 5.5 ms "gap" was not a bench-vs-server property: it was an unrepeatable slow state of the old bench run (large SD; the S2 notes also show the Q4 control running ~100 tok/s early that day vs ~142 later). I could not identify its cause (candidates: cold GPU/CPU clocks after model load, background load; [unv]). The honest explanation is therefore: "not a real gap; the 51 was an outlier measurement", plus a small real ~0.46 ms/token server-side cost (CPU-side sampling/logits readback/slot loop; B2 tests the sampling part).
- Server logs show `graphs reused = 9109` of 9216 decoded tokens (99 %; the ~3 non-reused per request are the prompt/first tokens), `graph reallocs = 0`: no per-token graph rebuild in either flag set. [measured]

## B2: backend (GPU) sampling, greedy
Flag: `-bs` / `--backend-sampling` ("experimental", default off; confirmed in `llama-server --help`). Greedy (temperature 0) requests, same prompts/method as above; `-np 1 -kvu` unless noted. Host-side vs GPU-side argmax: the only switch in this build is `-bs` (CPU sampler over the 248k-logit row, ~1 MB copied per token, vs argmax on the GPU with only the token id copied), so "without -bs" = host argmax and "with -bs" = GPU argmax; a request-level `top_k=1` was tested with and without `-bs` as a second view [measured].

### Headline [measured]
- Clean re-run block with tight controls (control 68.20 +/- 0.06 before and 68.16 +/- 0.15 after): `-bs` = **70.94 +/- 0.02 tok/s = 1.040x +/- 0.001** over plain CPU sampling. Greedy output is byte-identical to the control in 30/30 pass-prompt pairs.
- First block (noisier: the start control ran 65.5 +/- 2.5, one pass 61.6, the end control 68.1): `-bs` 69.96 +/- 0.64 (1.027x vs the end control, 1.047x vs the bracket mean), `-bs` + top_k=1 70.07 +/- 0.16 vs top_k=1 without `-bs` 67.13 +/- 0.55 (1.044x), `-bs` without `-np 1 -kvu` 70.23 +/- 0.39 vs 66.68 +/- 0.38 (1.053x). So the PR #17004 warning "backend sampling is slower without -kvu" did NOT apply here: it helped about equally with or without `-kvu`.
- `-bs` with CUDA graphs disabled: 64.40 +/- 0.14 (0.945x vs the end control): graphs matter as before; `-bs` does not replace them.
- The saving is ~0.55 ms per token (14.66 -> 14.10 ms, from 68.2 -> 70.9 tok/s), in line with the ~4-10 % estimate from the research note (the low end) [measured vs est].
- Note the machine-state drift: the same plain control measured 69.45 (B1 start), 68.2 (B2 re-run), 67.4 (B1 end) and 65.5 +/- 2.5 (B2 first start). Absolute tok/s are therefore comparable only inside a block; only the ratios are used.

## B3: native MTP on the bf16 target
Flags (from `llama-server --help`): `--spec-type draft-mtp --spec-draft-n-max N --spec-draft-p-min P`. Target = **bf16 GGUF** (it contains the MTP block, see above), `-np 1 -kvu -c 4096`, greedy, same free-text prompts. "accept" = draft_n_accepted / draft_n from the server timings; "tok/cycle" = generated tokens / verify cycles (cycles = tokens - accepted); "cycle ms" = generation time / cycles. Plain control cycle = one token = 14.7 ms. [measured]

### Headline [measured]
- Plain bf16 control, bracketing the main sweep: 68.14 +/- 0.03 (start), 69.09 +/- 0.09 (mid), 69.04 +/- 0.07 tok/s (end); drift 1.3 %.
- **n-max 1, default p-min: 74.10 +/- 0.13 tok/s = 1.088x**; acceptance 62.8 %, 1.62 tokens per cycle, cycle 21.9 ms (vs 14.7 ms plain). n-max 2: 72.55 (1.065x, accept 49.7 %, 1.98 tok/cycle, 27.3 ms). n-max 3: 64.77 (0.951x, accept 37.4 %, 2.10 tok/cycle, 32.5 ms).
- A p-min gate HURT in every cell (0.84x-0.94x): it raises the acceptance of drafted tokens (85-95 %) but most cycles then draft nothing or one token, so tokens per cycle fall to 1.26-1.64 while the cycle cost stays 21-27 ms. So the research note's suggestion to use a probability gate did not work on this model [measured].
- Cost model check: cycle = 14.7 ms + ~7.2 ms for one draft + a 2-token verify at n-max 1; each extra drafted token adds ~5.4-5.2 ms. That matches the research estimate that the MTP draft costs ~5.5 ms with the full 248k head (the head is read again per draft token) [measured, est confirmed].
- **Best configuration so far: bf16 + MTP n-max 1 + `-bs`: 79.18 +/- 0.07 tok/s = 1.147x +/- 0.002** against bracketed plain controls (69.09 / 69.01). Same MTP config without `-bs` in the same block: 75.17 +/- 0.09 = 1.089x. Backend sampling adds about +5 % on top of MTP (cycle 21.6 -> 20.5 ms). Greedy output is identical to plain bf16 in only 10 of 30 (prompt x pass) cases: speculative verification uses different kernels and the text diverges after a while (still greedy output of the same model, not scored for quality). No loops (0/6 prompts, every config).
- This is a free-text result: acceptance 63 % is in line with the Q4 S2 measurement (64 %); the n-max 1 gain is small but real, unlike the ~0.99x on the Q4 target, because the bf16 token costs 14.7 ms and the MTP draft costs a smaller fraction of it.

### Different target (clearly NOT bf16) [measured]
Unsloth MTP Q4_K_M as target: plain 148.05 +/- 0.62 tok/s (this is 2.16x the bf16 control, only because it is a 4-bit model); with MTP n-max 1/2/3: 146.86 / 142.35 / 126.27 tok/s = 0.992x / 0.962x / 0.853x of its own plain control (accept 64 % / 51 % / 40 %). So on the Q4 target MTP does not help free text, consistent with the earlier S2 result; the gain exists only for bf16 where the plain token is slower.

### Bonus: Q4_K_M as draft for the bf16 target (`-md`, draft-simple) [measured, one config]
`--spec-type draft-simple -md Qwen_Qwen3.5-0.8B-Q4_K_M.gguf -ngld 99 --spec-draft-n-max 2 --spec-draft-p-min 0.6`: **34.61 +/- 0.16 tok/s = 0.505x** (cycle 47.8 ms). The logged acceptance is 99 % but only ~95 tokens per 256 were drafted (p-min 0.6 gates most) and the draft step is very slow in this build for this hybrid model (hypothesis [unv]: the recurrent draft state is re-evaluated rather than rolled back). Only this single setting was tried; other n-max / p-min values were not.

## Conclusion (plain language)
- The old "bf16 is only 51 tok/s in llama-bench" number was an outlier; today llama-bench gives 71.7 and the server 68-69.5 tok/s (about 3 % slower than bench). There is no big hidden overhead gap to remove, and no environment variable or flag makes plain bf16 faster than the default (graphs, fusion and graph reuse are already on and each is worth 3-8 %).
- Two flag-only changes did help: backend sampling (`-bs`, +4.0 %, tightly measured) and native MTP with one draft token (+8.8 % to +9.6 %). Together: **79.2 tok/s, 1.15x** over plain bf16 on free-text greedy replies. This is far below the 300 tok/s goal; the research note's estimated ceiling for lossless llama.cpp-only methods (1.2-1.5x [est]) is approached only at its low end.
- Longer drafts and probability gates do not help on free text because acceptance falls fast (63 % -> 37 %) and each extra draft token re-reads the 508 MB output head; the Q4 same-model draft is much worse (0.5x).
- Next lever according to the cost model: make the MTP draft cheaper (trimmed draft head, B4; ~5.5 ms -> ~2.3 ms [est]) which would turn n-max 1-2 into roughly 1.3x [est].

## Caveats, skipped items
- Machine-state drift of 1-4 % within and between blocks (and one early outlier); only same-block ratios are used. Background apps (Taskmgr, OEM software, chat apps) were running on the PC and could not be closed (no system settings were changed), so single noisy passes (e.g. 61.6 tok/s in the B2 first control) happen.
- 6 free-text prompts, one reading per config of loop metrics (pass 1), greedy only; no temperature > 0 runs, no quality scoring of speculative outputs (20 of 30 outputs differ from plain greedy). The generated lengths are 256 tokens (512 in one test).
- The cause of the old 51 tok/s measurement was not found. `GGML_CUDA_GRAPH_OPT`, f16, ctx and length have no effect; `-bs` effect with other samplers (top-p/temperature) not tested. Only one Q4-draft setting tried; trimmed-head (B4), megakernel probe (B6), Nsight profile and kernel work (B7) were not done. Parallel/skeleton/batching methods are excluded by the task.
- Raw data: B1 `...B1-overhead.raw.json.gz`, B2 `...B2-backend-sampling.raw.json`, B3 `...B3-mtp.raw.json.gz` (gzip because >200 KB). Scripts: `scripts/bf16_bench.py`, `bf16_report.py`, `gguf_tensors.py`, `b*_run*.ps1`.
