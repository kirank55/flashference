# bf16 free-text speed-up experiments, Qwen3.5-0.8B (2026-10-26)

Goal: speed up ONE continuous free-text reply, single stream, non-quantized (bf16) 0.8B target. No parallel/batched/sub-task methods.
Hardware: RTX 3050 Laptop 4 GB, i5-13420H, plugged in, Balanced plan; nothing in the system was changed. llama.cpp CUDA b11884 (commit 63412d873).
Labels: **[measured]** = measured here, **[est]** = estimate from the research note (not measured), **[unv]** = unverified guess.

## Method (all sessions)
- Prompt set: the 6 free-form prompts F1-F6 from prompts/prompts.json (essay, story, explanation prompts; no copy-heavy prompts). Chat template, thinking disabled, greedy (temperature 0, seed 1), `cache_prompt=false`, n_predict 256 (all six reached 256 tokens in every pass; except the 512 test where F1 stopped at EOS after 326).
- Server configs: fresh llama-server per config, GPU-idle check before each (nvidia-smi 0 % util, <300 MiB used, no stray llama processes), one warm-up pass over the 6 prompts discarded, then 5 timed passes. One pass = sum(generated tokens)/sum(server `predicted_ms`) over the 6 prompts. Mean +/- SD is over the 5 passes. Common flags: `-ngl 99 -fa on -np 1 -kvu -c 4096`, `-t/-b/-ub` default (the server resolves `-t` to 8, `-b 2048 -ub 512`).
- llama-bench configs: `-p 0 -n 256 -r 5` (bench discards its own warm-up); mean +/- SD of 5 reps. Bench default is `-t 8`, `-fa` explicit on, no sampling.
- Speedup = config mean / control mean (+/- propagated SD). The control (plain bf16 server) is re-run at the end of each session. "vs control" in the first table uses the mean of the start and end controls (bracket mean); where drift matters I also quote the adjacent control.
- Raw data: `2026-10-26-bf16-B1-overhead.raw.json.gz` (B1), `...-B2-backend-sampling.raw.json`, `...-B3-mtp.raw.json` (B2/B3 added below). Server logs are in logs/ (git-ignored).
- Loops: for every pass I compute the duplicate-4-gram rate and the max repeat count of any 6-word sequence; "loop" = dup4 >= 0.30 or some 6-gram >= 3 times.

## Is the model really bf16?
`scripts/gguf_tensors.py`: the bf16 GGUF (`Qwen_Qwen3.5-0.8B-bf16.gguf`, 1.56 GB) has all weights as BF16 (type 30) and **already contains the MTP block** (`blk.24.nextn.*`, `nextn_predict_layers = 1`, the Q4_K_M bartowski file too). So MTP on the bf16 target works with the existing file; no download was needed [measured]. The f16 GGUF used in B1 was made with `llama-quantize --allow-requantize <bf16> <f16> F16` (4 s).

## B0/B1: reconciling llama-bench vs llama-server, then overhead toggles
Env var names present in this build (strings in the DLLs) [measured]: `GGML_CUDA_DISABLE_GRAPHS`, `GGML_CUDA_GRAPH_OPT`, `GGML_CUDA_DISABLE_FUSION` (ggml-cuda.dll), `LLAMA_GRAPH_REUSE_DISABLE` (llama.dll). All four exist. `-bs/--backend-sampling` exists.

### Short answer: the 51 vs 71 tok/s gap did NOT reproduce
- llama-bench today, bf16, `-ngl 99 -fa on -p 0 -n 256 -r 5`: **71.74 +/- 0.10 tok/s**; with the earlier baseline's exact style (`-p 512 -n 128`): 71.54 +/- 0.11; with `--no-warmup`: 70.42 +/- 0.03. The old baseline file said 51.47 +/- 4.93 (r=3, taken at ~09:50 in the same day, first model run of the day, SD of 10 %). [measured]
- The server with identical flags: 69.45 +/- 0.20 (start control). Real remaining bench-over-server gap: **+3.3 % (13.94 vs 14.40 ms/token, 0.46 ms)**. `-np 1 -kvu` vs `-np 1` vs auto slots make no difference (69.59 / 69.56 vs 69.45; within 0.2 %). [measured]
- So the 5.5 ms "gap" was not a bench-vs-server property: it was an unrepeatable slow state of the old bench run (large SD; the S2 notes also show the Q4 control running ~100 tok/s early that day vs ~142 later). I could not identify its cause (candidates: cold GPU/CPU clocks after model load, background load; [unv]). The honest explanation is therefore: "not a real gap; the 51 was an outlier measurement", plus a small real ~0.46 ms/token server-side cost (CPU-side sampling/logits readback/slot loop; B2 tests the sampling part).
- Server logs show `graphs reused = 9109` of 9216 decoded tokens (99 %; the ~3 non-reused per request are the prompt/first tokens), `graph reallocs = 0`: no per-token graph rebuild in either flag set. [measured]


### One-at-a-time toggles (server unless noted) [measured]
Ratio column uses the ADJACENT start control (69.45 +/- 0.20) for configs run in the first block; the control drifted -3.0 % (69.45 -> 67.38) over the ~45 min session, so the last three configs (gen512, f16, threads8) were re-run in a second block bracketed by new controls (second table below).

| `-np auto` / `-np 1` / `-np 1 -kvu` | 69.56 / 69.59 / 69.45 | 1.002x / 1.002x / 1.000x | no effect on this build |

| bench `-t 4` vs `-t 8` | 70.05 +/- 0.42 vs 71.74 | 0.976x | 8 threads slightly better |

Conclusion for item 1: **nothing in flags/env makes bf16 decode faster than the default**; every toggle is neutral or worse. The default already has CUDA graphs, fusion and graph reuse on. The only gap left versus llama-bench is ~3 % (0.46 ms/token) of server-side per-token work.
