Setup/method = B0-B4 (Qwen3.5-0.8B **bf16 target**, llama.cpp CUDA b11884, hybrid own build reusing release CUDA DLLs, greedy, chat template, thinking off, cache_prompt=false, n_predict 256, fresh server per config, GPU-idle check, 1 discarded warm-up + 5 timed passes [3 for the E2-E4 sweeps], `-bs`). Prompt sets: free F1-F6, rep (copy-heavy C1-C6, `prompts.json`), code K1-K4 + lang L1-L4 (`prompts/e-prompts.json`: es, de, zh, hi). Labels: [measured] / [est] / [unv].

**Session caveats [measured].** (1) The GPU was shared with an external Hyper-V worker (`vmwp.exe`, ~100 % 3D util, 2-3.7 GB VRAM) for long stretches of this session; runs were gated on an idle GPU (`wait_idle`) and any config with >4 % pass spread (or <55 tok/s, i.e. slower than plain) is rerun. A first queue was contaminated and its affected keys were deleted and rerun. (2) Machine drift: plain bf16 free = 65.24 (start of E1) vs 68.45 tok/s (end control `e1-free-plain-end`), i.e. ~5 %; B4's day was ~69. Ratios in the tables are vs the same-set plain control measured earlier in the queue, so free-text ratios are ~3 % pessimistic vs the end control. (3) "out = plain" = number of (prompt x pass) outputs byte-identical to plain greedy; speculative verification batches change fp reduction order, so even untrimmed MTP is not byte-identical to plain on every prompt (10/30 on free text; same as in B4). "Lossless" below therefore means: *trim/E-patches change only drafts; the output equals the untrimmed-MTP output of the same build/prompt, and the full bf16 target verified every token*.

Findings [measured]:
- **Free text:** trimmed 8k = 107.2 tok/s = 1.64x the start-of-session plain control (65.2) and ~1.57x the end control (68.3); B4's 1.60x is reproduced. Untrimmed MTP is only 1.15x, so the head trim is the whole gain. Trimmed 8k output == untrimmed MTP output (30/30 pairs); 10/30 are byte-identical to plain greedy (the other 20 differ only through bf16 batch-order numerics, same as untrimmed).
- **Code:** untrimmed has high acceptance (74.1 %) but is slow (93.7 tok/s, 1.41x); trimmed 32k keeps 68.5 % and reaches **124.9 tok/s = 1.88x** (best code config). Trimmed 8k n2 loses acceptance (42.9 % in the invalid run; the ranking corpus is English prose), trimmed 8k n1 = 92.1 tok/s (1.39x). The clean 5-pass `e1-code-trim8k-n2` run is **not available** (two attempts hit a GPU stolen by the external VM, then CUDA vanished, see "Blocker").
- **Non-English (es/de/zh/hi):** untrimmed MTP acceptance is only 39 % and gives 1.00x; trimming drops it to 12-20 % (1.01-1.05x). The English-frequency vocabulary is the problem -> motivates E4.
- **T=0.7, top-p 0.9:** trimmed 8k with greedy draft sampling = 104.8 tok/s (1.56x the t07 plain 67.3, 1.50x of plain+`-bs` 70.2), probabilistic draft sampling 105.7 (acceptance 46.1 vs 45.0 %); n-max 1 = 95.4 (acceptance 60.1 %). Untrimmed + probabilistic = 77.7. Sampling-mode speculative decoding stays lossless in distribution (standard rejection sampling), outputs are not comparable byte-wise to plain (different RNG consumption).

## E4 - context-adaptive draft vocabulary: implemented, smoke-tested on CPU, GPU speed NOT measured
- Patch (same file): `LLAMA_MTP_TRIM_K=8192 LLAMA_MTP_TRIM_FIXED=4096 LLAMA_MTP_DYN=16`: rows [0,4096) of the trimmed draft head are the fixed English-frequency tokens; rows [4096,8192) are rewritten every 16 generated tokens (an 8 MiB host->device copy only when the set changes) with (1) the most recent distinct context tokens, (2) all tokens of the non-Latin script classes (CJK, Indic, Cyrillic, Arabic/Hebrew, Hangul, Thai, Greek) that make up >=20 % of the last 256 context tokens (ids in BPE order ~ frequency), (3) the rank-order default fill. The draft head stays a fixed `[1024, 8192]` tensor + token map, the target still verifies every token, so the output cannot change.
- **CPU smoke test, 40 tokens, `-dev none` (`scripts/e_smoke.py`) [measured, tiny sample]:** zh prompt: trimmed 8k 1 of 73 drafts accepted vs dynamic 14 of 47; hi prompt: 5 of 67 vs 23 of 30; code K3: 21 of 36 vs 21 of 36; **generated text identical** to trimmed-8k in all three. So acceptance on non-English recovers from ~2-7 % to ~30-75 % on these samples; the full-length GPU speed/acceptance numbers (`e4-*` configs) were not run [unv]. Expected [est]: lang acceptance towards the untrimmed 39 % plus context hits, i.e. roughly 1.3-1.5x vs plain on non-English instead of 1.0x.

## E2b - multi-candidate / tree drafts: infeasible here (source reading, [measured] from b11884 code)
- The server verifies **one linear draft per sequence**: `common_speculative_draft` returns a flat `llama_tokens`; the target batch is `[id_last, d1..dn]` with one sequence id and a causal mask. There is no draft-tree / `parent` array, no tree attention mask and no per-branch KV/recurrent-state fork in `tools/server` or `common/speculative.cpp` (the only multi-sequence path is `n_seq` parallel *requests*).
- Qwen3.5 is a hybrid (Gated-DeltaNet recurrent layers + attention). A tree would need one recurrent state per branch (or a tree-structured GDN scan); llama.cpp's recurrent-state cells are per sequence and rolled back by whole-draft `seq_rm`, not per branch. A "k parallel linear drafts" fallback (k sequences, k x verify cost) multiplies verify work (the target's body+head are the 2/3 of per-token time we are trying to save) and also needs state copies per branch; expected gain at ~50 % per-token acceptance is small: P(first token right) rises only from top-1 (~0.5-0.6) to top-2 (~0.7) while verification cost doubles. [est]. Not attempted.

## E5 - exact (lossless) trimmed target output layer
Question: can the target's 248k x 1024 bf16 head (485 MiB read every verify cycle, ~1/3 of per-token time) be replaced by a cheaper first pass plus an exact fallback, so the greedy argmax is still *identical*? Study on the CPU with real data (`scripts/e5_collect.py`, `e5_analysis.py`, `gguf_read.py`; raw `results/2026-10-27-bf16-E5-analysis-enfree.{json,txt}`): 2560 final hidden states (English free-text prompts, bf16 target on CPU `/embedding`), head matrix read from the GGUF. [measured on the CPU analysis, not on the GPU]
- Sanity: argmax of the exact head == generated token 99.80 % (the 0.2 % is CPU-vs-GPU fp noise). Top-1 vs top-2 gap: median 1.86, 25 % < 0.69, 8.5 % < 0.2, 2.5 % < 0.05 - i.e. margins are thin often, so a *small fixed margin threshold* is not safe; a *rigorous bound* is needed.
- Rigorous bound: quantised row `q_i` with `|e_i - q_i|_2 <= eps_i` (measured per row) gives `|h.e_i - h.q_i| <= |h| eps_i` (Cauchy-Schwarz). Certified argmax if best lower bound > every other upper bound; otherwise candidates = rows whose upper bound >= best lower bound, re-scored exactly with their bf16 rows (gather).

| first-pass head | bytes vs bf16 | argmax certified with NO bf16 row read | candidates needing exact re-score (mean / <=4 / <=16 / <=64) | plain argmax of quantised head == exact |
|---|---|---|---|---|
| Q8_0 (8.5 bit) | 0.53 | 68.0 % | 1.6 / 96.9 % / **100 %** / 100 % | 99.69 % |
| Q6 (6.5 bit) | 0.41 | 30.3 % | 8.4 / 57.6 % / 86.1 % / 98.8 % | 98.36 % |
| Q5 (5.5 bit) | 0.34 | 12.5 % | 92.6 / 27.7 % / 46.4 % / 69.2 % | 96.56 % |
| Q4 (4.5 bit) | 0.28 | 0 % | 8730 / 0.2 % / 2.7 % / 9.9 % | 93.91 % |
| low-rank 128/256/384 (SVD of head) | 0.125/0.25/0.375 | 0 % | all 248320 (spectrum is flat: rank-512 holds only 71 % of the energy) | - |

- **Result [measured on 2560 positions]:** a Q8_0 first pass + exact bf16 re-scoring of <=16 gathered rows certifies the true bf16 argmax at **100 % of positions** (68 % with no gather at all; 96.9 % need <=4 rows). So an *exactly lossless* head with ~0.53x of the head bytes (plus 16 x 2 KiB rows) exists in principle. Q6 and below are not useful (candidate sets blow up); low-rank is useless.
- Expected speedup [est]: head is ~1/3 of the 14.6 ms/token plain step and ~1/4-1/3 of a ~17.8 ms verify cycle (2 drafts); halving its bytes saves ~1.3-2 ms per cycle (head matmul is memory bound, 3 rows read the weights once) => **~+8-11 % on top of the 110 tok/s B4 config, minus** the cost of the extra ops (top-k over 248k upper bounds, gather, small exact dot, certify flag, rare fallback). Realistic net +4-8 % [est]. The head-only-Q8 speed ceiling (non-lossless, `e5-*-q8head` rows) bounds what is possible.
- What a real implementation needs (not done): (1) a Q8_0 copy of the head next to the bf16 one (+258 MiB VRAM) and per-row error norms `eps_i` (248k floats, 1 MB); (2) in the target graph: Q8 `mul_mat` for logits `s_i`, `|h|`, upper bound `s_i + |h| eps_i`, `top_k` (k~17) over upper bounds [ggml has `top_k` CUDA], `get_rows` on the bf16 head for the k candidates, k exact dots, argmax, and certificate `ub_(k+1) <= max exact`; (3) a graph-level or host-side fallback to the full bf16 head when the certificate fails (observed 0 / 2560 for k=16, so rare but must be exact) - the host check costs a device sync per cycle unless the fallback is folded into a conditional/`ggml_cond`-style op, which ggml lacks, so the practical form is "compute both when uncertain" via a second graph launch on the rare path; (4) integration with backend sampling (`-bs` greedy sampler consumes logits) - the certified argmax replaces the logits tensor for the greedy sampler; with temperature > 0 the full distribution is needed and this trick does not apply. No custom CUDA kernel is strictly required (all ops exist in ggml-cuda), but the graph surgery + sync/fallback logic in `llama-graph`/`qwen35.cpp` and server sampling is a multi-day change, hence analysis-only here.
