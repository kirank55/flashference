# bf16 B4: lossless trimmed draft vocabulary for native MTP (2026-10-26)

Goal: cut the cost of the MTP draft step on the bf16 Qwen3.5-0.8B (tied 248k-vocab output head, ~508 MB bf16 re-read on every drafted token) by letting the DRAFT pick its token from the K most frequent token ids only (FR-Spec idea, llama.cpp issue #25187), while the bf16 target still verifies over the full vocabulary. Method, hardware and labels as in `2026-10-26-bf16-b0-b3.md` (greedy, F1-F6, 256 tokens, 1 discarded warm-up + 5 timed passes, fresh server per config, GPU-idle check, plain control re-run between blocks, ratios only). **[measured]** = measured here, **[est]** = estimate, **[unv]** = unverified.

## Headline [measured]
- **bf16 + MTP with an 8k-token draft head + `-bs`: 110.08 +/- 0.04 tok/s = 1.595x vs plain bf16 (n-max 2); 97.59 +/- 0.22 = 1.413x (n-max 1)**, against the previous best 79.23 +/- 0.04 = 1.148x (untrimmed, n-max 1 + `-bs`, same session). That is **+39 % over the previous best** (110.08 / 79.23).
- Output is the same as the untrimmed MTP output in 30/30 (prompt x pass) cases for n-max 1 and 2 (identical text hashes), as expected since the target verifies the full vocabulary. Like every MTP/speculative config here it is identical to plain greedy only for 10/30 (2 of the 6 prompts; the other 4 diverge late: first differing character at 1370/1463, 314/1127, 319/1527, 1019/1120). This divergence already exists for untrimmed MTP (B3, fp numerics of the batched verify) and is not caused by the trim. Outputs are deterministic across the 5 passes (1 distinct hash tuple).
- Best K is small: 4k-16k are within 1 % of each other; 32k costs ~2-3 %; 2k loses acceptance (44-58 %). n-max 2 now beats n-max 1 (1.595x vs 1.413x); n-max 3 / 4 give 1.58x / 1.58x (acceptance falls to 36 % / 30 %).
- Per drafted token the trim saves ~4.0 ms (cycle at n-max 2: 25.70 ms untrimmed -> 17.75 ms trimmed with K=8k, i.e. 7.95 ms for 2 drafts; n-max 1: 20.47 -> 16.52 ms). The untrimmed draft token cost ~5.3 ms (B3), so it falls to ~1.3 ms, close to the research note's ~2.3 ms estimate.

## Feasibility findings [measured]
- **CUDA toolkit is NOT installed** on the PC (no `nvcc`, no `C:\Program Files\NVIDIA GPU Computing Toolkit`). VS 2026 Build Tools (MSVC 14.50, `cl.exe`, Windows SDK 10.0.26100), CMake 3.29.2, Ninja, git, LLVM clang are present. A normal CUDA build would need the multi-GB CUDA toolkit; **I did not install it**.
- **Route that worked without any install: hybrid build.** The patch only touches `src/` and `common/` (CPU/host code and the compute-graph description), not `ggml-cuda`. So I built llama.cpp b11884 (tag `b11884` = commit `63412d873`, cloned with `git clone --depth 1` + `git fetch --depth 1 origin tag b11884` into `llama-src/`, git-ignored) with MSVC and `-DGGML_CUDA=OFF -DGGML_BACKEND_DL=ON`, and dropped the release's prebuilt `ggml-cuda.dll`, cuBLAS DLLs and `ggml-cpu-*.dll` next to it (folder `llama-cpp-b4/`, git-ignored; `llama-cpp/` untouched). `scripts/b4_build.cmd` / `scripts/b4_rebuild.cmd` rebuild it (~3 min). Sanity check: the unpatched-behaviour config on this build (`own-n1-bs`, no trim env var) = 79.14 +/- 0.10 tok/s vs 79.23 +/- 0.04 for the release binary, outputs identical 30/30, and `own-control` (plain) 68.89 vs 69.01: **the hybrid build is as fast as the release build**.
- **No-rebuild GGUF route: not feasible as such.** In b11884 `qwen35.cpp` loads the optional `blk.N.nextn.shared_head_head.weight` with shape `{n_embd, n_vocab}` (falling back to the tied `token_embd`), so a smaller head tensor in the GGUF fails the shape check, and the Qwen3.5 MTP graph has no `d2t`-style scatter (EAGLE-3's `eagle3.cpp` has one, MTP does not). A GGUF edit can only change the head's *quantization* (e.g. a Q4/Q8 `shared_head_head` copy: 2-3.5x fewer bytes but still 248k rows and a lossy draft head); **I did not test that variant** [unv: would save maybe half of the 4 ms].
- Issue #25187 (read via the web, not cloned on the PC): "FR-Spec-style draft-vocab trimming for native MTP" by avifenesh; his branch `avifenesh/llama.cpp` `frspec-mtp-vocab-trim` (commit `047bfa508`) sizes `output.weight` from a `d2t` tensor in an MTP-only draft GGUF and scatters the compressed logits back to full-vocab shape with `ggml_set_rows` inside the graph (needs a trimmed draft GGUF produced offline). He reports -85 % time in the draft LM-head matmul (K=32768 of 248k), +1-3 % e2e on a 27B, byte-identical greedy output; other commenters report 5-10 pp lower acceptance at 32k on other workloads and +9 % on a bandwidth-starved iGPU. The issue was auto-closed as stale, reopened 2026-10-21 after ggerganov wrote "we'll support it eventually" after refactoring. **My patch uses a different mechanism** (below); it needs no GGUF change.

## What was built
`patches/b4-trim-draft-head.patch` (185 lines, against b11884; apply in `llama-src/` with `git apply`):
- `src/llama-model.cpp` `load_tensors_mtp_trim()`: if env `LLAMA_MTP_TRIM_FILE` (text file, one token id per line, most frequent first) and `LLAMA_MTP_TRIM_K` are set and the model is qwen35 with an MTP block, read the head rows (`shared_head_head` or tied `output`) back, gather the first K ranked rows into a new `[n_embd, K]` weight tensor on the same backend buffer, plus a `[n_vocab]` f32 mask (0 for i < K, -inf otherwise). No-op otherwise.
- `src/models/qwen35.cpp` `graph_mtp`: when the subset exists, logits = `mul_mat(subset, h)` (K rows), `ggml_pad` to n_vocab and add the mask, so the output row keeps its full shape (index i < K = subset index) and `-bs` GPU argmax / the CPU sampler work unchanged; the K-row matmul is the saving.
- `common/speculative.cpp` (draft-mtp): the sampled/candidate ids are subset indices; map them back to token ids with `llama_model_mtp_trim_map()` (new function in `src/llama-ext.h`) before they are returned as the draft. The target graph, its logits and the verification are untouched, so the verified output is the bf16 target's.
- Scoped to Qwen3.5 dense MTP, requires an unscaled head (no `_s` scale tensor); everything else falls back to the untrimmed path (warning logged).

Ranking: `scripts/b4_rank_tokens.py` tokenises a held-out text corpus with `llama-tokenize` (the same GGUF vocab): wikitext-2 test + all strings in the earlier S1/S2/S3/parallel-subtask raw jsons + every repo markdown file (2.1 M chars, 528,557 tokens, 21,254 distinct ids); special/EOG ids (`<|im_end|>`, `<|endoftext|>`, `<|im_start|>`, `<think>`, `</think>`) first; unseen tokens in id order (byte-level BPE ids roughly follow merge order); output `2026-10-26-bf16-b4-token-rank.txt`. The bf16 F1-F6 plain *outputs* are NOT in the ranking corpus, so coverage on them is a held-out check: top 4k / 8k / 16k / 32k / 64k ids cover **89.9 / 94.4 / 96.5 / 98.0 / 99.5 %** of the 1536 generated tokens. Caveat: the F1-F6 prompts are English prose on which the K choice was tuned; code or other languages will have lower coverage (not measured).

## What this means [measured unless noted]
1. The 248k tied head really is the draft bottleneck: shrinking it to 8k rows saves ~4 ms per drafted token and turns MTP from 1.15x into 1.41x (n-max 1) / 1.60x (n-max 2), still output-identical to untrimmed MTP.
2. The optimum moves: with a cheap draft step, drafting 2 tokens pays (acceptance of the 2nd token is still ~35 %); n-max 3-4 gain nothing more (acceptance 36 % / 30 %, longer verify batch).
3. Acceptance loss from the trim is small on English prose (62.8 % -> 61.8-62.4 % at 8-16k n-max 1; 49.7 % -> 48.3-48.8 % n-max 2) and grows below 4k (58.2 % at 2k). Workloads far from the ranking corpus (code, other languages) will lose more [unv, issue comments report 5-10 pp at 32k on their workloads].
4. Remaining gap to a 1-token plain step: the n-max 1 trimmed cycle is 16.5 ms for 1.61 tokens (plain 14.5 ms per token), so ~2 ms of the cycle is the draft step plus the verify batch of 2.
5. Unverified / untried: other K ranking corpora, an adaptive per-prompt vocabulary, temperature > 0 (the patch passes mapped candidate ids to the rejection sampler, untested), quantized draft head, applying the same trick to the target head (lossy, not done), upstreaming.
